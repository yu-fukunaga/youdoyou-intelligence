# スペック作成

## 目的

タスクの目的・背景と具体的な手順を記録した仕様書を `spec/` に生成する。

---

## ファイル命名規則

```
spec/NNNN-{kebab-case-name}.md
```

- `NNNN`: 4桁ゼロ埋めの連番。`spec/`直下(`spec/done/`含む)の既存ファイルの最大番号+1を使う
- `{kebab-case-name}`: 機能・タスク名をケバブケースで

---

## 作成手順

1. `ls spec/*.md spec/done/*.md` などで既存ファイルの連番を確認し、次の番号(4桁ゼロ埋め)を決める
2. `date -u +"%Y-%m-%dT%H:%M:%S.000Z"` で現在時刻(ISO8601)を取得する
3. ユーザーの指示とコードの文脈から、下記フォーマットに従って front matter + spec 本文を生成する
4. 不明な点はコードを読んで把握する。それでも不明なら確認する

---

## フォーマット

front matter は必須。すべてのspecファイルの先頭に付与する。

````markdown
---
id: "0013"
status: "backlog"
created: "2026-07-07T12:37:57.634Z"
modified: "2026-07-07T12:37:57.634Z"
completedAt: null
labels: ["client"]
epic: "機能追加・改善"
order: ""
---

# {機能名}

## Overview

（なぜこれを作るか。どんな問題を解くか。1〜3文）

---

## Details

（調査段階で書き足していくメモ。バグ一覧・改善案のように複数項目を積み上げる場合は`### バグ一覧` / `### 改善案`のようなチェックリストにしてもよい。各項目は端的に一行で書く）

---

## Operation

（タスク開始段階で、着手する項目ごとに追加する）

### Task 1: {タスク名}

（何をするか。どのファイル・関数・APIを変えるか。具体的に。ただしコードレベルの詳細を書きすぎない — それはコミットの役割）

### Task 2: {タスク名}

（同上）

...（タスクの数に上限はない。必要な数だけ追加する）
````

front matter の各フィールド:

- `id`: ファイル名の連番部分(`NNNN`)のみ（例: `0013`）。ファイル名をリネームしてもidを書き直さずに済むようにするため
- `status`: 新規作成時は常に `"backlog"`
- `created` / `modified`: 手順2で取得したISO8601タイムスタンプを同じ値で設定
- `completedAt`: 新規作成時は常に `null`
- `labels`: 変更が及ぶ領域を、リポジトリのルート直下ディレクトリ名(隠しディレクトリ含む)で指定する。複数選択可。それ以外の値は使わない
  - `ls -d */ .*/ ` 等でその時点のルート直下ディレクトリを確認し、そこから選ぶ(例: `client`, `server`, `.github` など。ディレクトリが増減すれば選択肢も追従する)
- `epic`: タスクの種別を表す固定カテゴリ。単一選択。以下のいずれか一つを設定する(それ以外の値は使わない)
  - `🍀 機能追加・改善`
  - `🐤 リファクタリング`
  - `🦑 バグ修正`
  - `🦔 品質基盤整備`(テスト・CI・precommitなど)
  - `🪼 開発ツール整備`(Makefile補完・agent skillなど、品質に直結しない生産性向上)
  - `🪽 ドキュメント整備`
- `order`: 新規作成時は常に `""`

---

## 運用フロー

specは一度に完成させるものではなく、以下の3段階で育てていく。

### 1. 初期作成段階

- タイトルと`## Overview`(大まかな目標)だけを決めて作成する
- やりたいことは、この時点で思いついた範囲を`## Details`にメモ程度で書いておいてよい。詳細を詰める必要はない

### 2. 調査段階

- 他のタスクをやりながら気づいたことや、このspecについて途中まで調べた内容を`## Details`に書き足していく
- バグ一覧・改善案のように複数の項目を並行して積み上げていく場合は、`### バグ一覧` / `### 改善案`のようなチェックリストにしてよい。この段階では各項目を端的に一行で書き、サブ箇条書きで詳細を書き込まない
- わかる範囲で`## Operation`まで軽く書いてもよい

### 3. タスク開始

- 着手する項目を、具体的に行動できるレベルまで落とし込み、`## Operation`に`### Task N: {タスク名}`として記載する。書きながら詰めていってもよい
- 着手した項目は`## Details`側の記述を端的な一行に整理し直す(例: `- [x] {要約} — 詳細は`## Operation`のTaskN`)。同じ内容をDetailsとOperationの両方に書かない
- **Taskに実装の詳細(コードレベルで何をどう変更したか)を書きすぎない。それを見せるのはコミットの役割。** コミット差分には残らない情報(コマンドの実行ログ、調査結果、判断の経緯など)を書く

---

## 注意事項

- 「なぜ作るか」を中心に書く。実装詳細は書かない
